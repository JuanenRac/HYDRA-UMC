STATUS: PROPOSED - fills a gap the user explicitly flagged ("se me habra
olvidado cosas") between the previously-documented FDCAN1 STACK A bus
(docs/architecture.md section 4, README.md section 6) and the user's new,

de las 8 tarjetas esclavas ... alimentacion +24V de 10 pines, 10 pines

this file for the exact reconciliation.

--------------------------------------------------------------------------------
1. WHAT THIS CONNECTOR CARRIES
--------------------------------------------------------------------------------
Per the user's own explicit split: +24V power (10 pins), GND (10 pins),
+5V - plus what already exists on paper for this bus (docs/architecture.md
section 4): the FDCAN1 differential pair. Reading the user's message
carefully, "conexion spi" appears in the same run-on sentence as the STACK A
connector - this is interpreted here as re-confirming the ALREADY-DOCUMENTED
STM32H745<->CM5 SPI1 link (README.md section 10), not a second bus riding on
this connector. FDCAN1 remains this connector's only command/data bus,
consistent with every prior document this session (docs/architecture.md
sections 1 and 4, README.md section 6). If that reading is wrong, tell me
and this file gets a real SPI_STACKA_* pin group instead of the reserved
spares below.

Two things had to be ADDED beyond the user's literal list, because a 40-pin
parallel bus serving 8 independently-populated slots cannot work without
them:

  - SLOT_ID[2:0]: a 3-bit hardware strap, PROPOSED as three pins on the
    connector, each pulled to a different logic level depending on WHICH of
    the 8 physical backplane drops a Robot Controller Board is plugged into
    (e.g. resistor-coded per drop on a shared backplane PCB, or jumper-
    coded on a ribbon harness). This is what lets each board self-identify
    its own N (0-7) at boot and compute its own FDCAN1 slot base ID
    (CAN_ID_STACKA_BASE + N*0x20, docs/architecture.md section 4) instead
    of needing that ID hand-programmed into firmware per board. Without
    this, the addressing scheme already on paper has no way to actually
    assign N to a physical board.
  - BOARD_PRESENT: one open-drain pin, pulled low by an installed Robot
    Controller Board, read by the Kinematic Brain to know which of the 8
    slots are physically populated without needing a full FDCAN handshake
    first (useful at power-up, and for HYDRA-UMC-STUDIO's Flasher/Tester to
    show "not installed" vs. "installed but not responding").

3. PHYSICAL TOPOLOGY - CONFIRMED: a physical stack, not a backplane/harness
--------------------------------------------------------------------------------
CONFIRMED by the project owner: the 8 Robot Controller Boards mount as a
physical STACK - one on top of another - on one side of the Kinematic
Brain's own PCB, not spread across a separate backplane board or connected
by ribbon cables (this section previously proposed both of those as
options; the user has since settled it - keeping the old reasoning below
struck through only in spirit, replaced here, not left ambiguous).

    Kinematic Brain PCB
    +----------------------------+
    |                            |
    |   [ STACK A OUT connector ]|--+  <- this 40-pin definition, base of the stack
    +----------------------------+  |
                                     v
                          +-------------------+
                          | Robot Ctrl Board 1 |  SLOT_ID=0
                          | [IN, passthrough]  |--+  <- 2 connectors: one mates
                          +-------------------+  |     downward into the board
                                                  v     below, one extends the
                          +-------------------+        SAME 40 signals upward
                          | Robot Ctrl Board 2 |  SLOT_ID=1  for the next board
                          | [IN, passthrough]  |--+
                          +-------------------+  |
                                     :            v
                                     :     ... up to 8 boards, SLOT_ID=7
                                     :
                          +-------------------+
                          | Robot Ctrl Board 8 |  SLOT_ID=7
                          | [IN only - top]    |
                          +-------------------+

Each Robot Controller Board (except the topmost) carries TWO of this same
40-pin connector: one on its underside mating with the board (or the
Kinematic Brain) below it, one on its topside extending the identical 40
signals to whatever mounts above it - a straight-through passthrough, every
pin wired 1:1 between the two connectors on a given board, exactly like a
Raspberry Pi HAT's own stacking header convention (same idea, this
project's own pin count/pinout, not the Pi's). This is what makes "each
slave board gets a 40-pin connector" (the user's own robot_controller_
board_stm32g474/BOM.TXT precedent) and "en paralelo, una encima de otra"
(physically stacked, electrically parallel - the user's own words) the SAME
design decision: every board taps the identical 40 signals via its own
pair of stacking connectors, nothing routes through any board's own logic
to reach the next one up.

CAN bus implication: FDCAN1 (CAN1_H/CAN1_L, pins 25-26) is now a genuine
multi-drop stack instead of a backplane trace - 120ohm termination
resistors belong at the two electrical ends: the Kinematic Brain's own
STACK A OUT connector, and the TOPMOST populated Robot Controller Board's
own upward-facing connector (populate/depopulate a termination resistor
per board as stack height changes, or fit a keyed terminator plug on top
of however many boards are actually stacked) - same standard CAN
termination practice as before, just at physically different points now
that the topology is a stack instead of a backplane run.

4. CONNECTOR PART / MECHANICAL
--------------------------------------------------------------------------------
PROPOSED: 2x20, 2.54mm-pitch STACKING header/socket pair (not a plain box
header - see section 3's own stack diagram) - this UPDATES, not
contradicts, README.md section 11's previous "Heavy-copper shrouded
connector, 2.54mm pitch" line, which was written before the pin COUNT or
the physical stacking arrangement was known. Same pitch as originally
specced, now with an exact pin count, a per-pin current budget (10
parallel contacts per rail), and a real mechanical form factor behind it.
Candidates: 2x20 female stacking headers (the same family Raspberry Pi
HATs use, e.g. Samtec SSQ/ESQ or Adafruit-style long-leg stacking headers)
sized for however many boards' worth of stack height the mechanical design
needs to clear per board, high-current-rated contacts given the 10-pin-
parallel +24V/GND rails. Exact part number and stack pitch (how much
vertical clearance each board needs) TBD at schematic/mechanical-design
time - not decided here.
